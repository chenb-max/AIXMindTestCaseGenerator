# 测试意图与用例质量规则

## Test Intent 定义

测试意图是“要验证的业务行为、规则、状态或风险”，不是完整测试用例。

```text
事实 → 测试意图 → 测试用例 → XMind
```

测试意图回答：

- 要验证什么？
- 为什么需要验证？
- 属于哪个场景分类？
- 使用哪种测试技术？
- 依据是需求、截图、流程还是风险推断？

测试用例才补充前置条件、具体数据、可执行步骤和可观察预期。

## 意图设计规则

1. 一个意图只验证一个核心风险或业务目标。
2. 先覆盖输入事实和主流程，再补充适用的异常和边界。
3. 没有输入依据的场景不要为了凑分类而生成。
4. 同一目标仅因数据变化产生的用例，应共享一个意图并区分测试数据。
5. 推断意图必须记录具体假设、来源和较低置信度。

## 常见测试技术映射

| 输入或风险特征 | 优先测试技术 | 典型意图 |
| --- | --- | --- |
| 有明确取值范围 | 边界值 | 最小值、最大值及相邻值的处理 |
| 有有限类别或格式 | 等价类 | 每个有效类别和代表性无效类别 |
| 多字段存在组合规则 | 决策表 | 条件组合对应的结果 |
| 页面或数据存在状态变化 | 状态迁移 | 合法转移、非法转移和恢复 |
| 多页面存在顺序和返回 | 流程测试 | 主流程、中断、返回和异常跳转 |
| 文件选择、校验和提交 | 文件上传测试 | 类型、空文件、失败、中断和结果一致性 |
| 快速多次点击或重复请求 | 重复提交测试 | 防重、幂等和只产生一次结果 |

只有在输入提供了相应约束时，才生成精确的边界值、类别或状态名称；未知约束只能生成确认型风险意图并记录假设。

## 用例质量标准

生成每条 Case 前后检查：

- 单一目标：只验证一个核心结果。
- 前置条件完整：执行前需要的登录、数据或状态已说明。
- 测试数据明确：数据可直接使用，或说明待替换变量。
- 步骤可执行：测试人员可以按步骤操作，不依赖隐藏动作。
- 预期可观察：能在页面、数据、状态或提示中验证。
- 来源正确：`visible`、`described`、`inferred` 与事实来源一致。
- 推断有假设：`inferred` 必须填写非空 `assumptions`。
- 优先级合理：核心业务和数据风险优先级更高。
- 不重复：不同标题但行为、数据和最终结果相同的用例应去重。

## Oracle 质量

预期结果必须描述用户可观察的结果。禁止只写：

- “系统正常”。
- “功能正常”。
- “上传成功”。
- “校验通过”。

应说明可验证对象、状态和结果，例如：

```text
页面停留在上传页，文件控件下方显示格式错误，且没有创建上传记录。
```

如果输入没有提供具体提示文案，不要编造文案；描述可观察的状态变化，并将不确定部分标记为推断。

## 生成前质量门禁

开始生成 Case Tree 前确认：

1. 没有无依据的页面、控件或业务规则。
2. 没有虚构的精确限制、权限或接口行为。
3. 测试意图之间没有明显重复。
4. 主流程和当前模式适用的核心风险已考虑。
5. 每个意图都有来源、优先级和置信度。
6. 预期结果具备可观察性。

门禁不通过时先修正内部意图，再生成 Case Tree。
