# 需求分析规则

## 目标

将需求文档、功能描述和用户补充整理为可测试的事实、规则、状态和验收目标，供页面/流程摘要和测试意图设计使用。

## 来源优先级

当不同来源出现冲突时，按以下顺序判断事实：

1. 用户在当前任务中明确补充的描述。
2. 需求文档明确写出的内容。
3. 页面截图中清晰可见的事实。
4. 页面标题、按钮文案和控件语义推断。
5. 通用测试风险推断。

高优先级来源不得被低优先级推断覆盖。无法消解的冲突必须在最终摘要中保留警告。

## 提取内容

优先提取以下信息：

- 功能目标和用户角色。
- 前置条件、输入、输出和验收标准。
- 字段约束、业务规则和状态变化。
- 页面顺序、动作和可观察结果。
- 成功、失败、取消、返回和恢复条件。
- 明确的优先级、风险或兼容性要求。

将原文事实与推断分开记录。需求没有说明的内容不要自动补成确定规则。

## 不得编造

除非输入明确提供，否则不要编造：

- 精确长度、大小、数量、时间或数值限制。
- 未展示的字段、按钮、下拉选项或页面。
- 用户角色、权限和审批规则。
- 接口路径、错误码、重试次数或超时值。
- 未描述的业务规则、数据关系或结果页。

可以提出风险测试意图，但必须标记 `source: inferred`，写出具体 `assumptions`，并降低 `confidence`。

## 缺失信息

缺失信息不阻塞主流程时：

1. 生成不依赖该信息的确定性用例。
2. 对风险推断生成低置信度意图或用例。
3. 在假设或 warning 中说明需要确认的内容。

只有在没有任何可用输入，或缺失信息会改变整个测试模式时，才向用户提出一个简短的阻塞性问题。

## 冲突处理

当需求和截图、流程描述之间不一致时：

1. 不要静默选择一方作为真相。
2. 分别记录冲突来源和冲突内容。
3. 生成可验证实际行为的用例时，标记 `inferred` 或低置信度。
4. 在最终响应中列出冲突，提醒测试人员确认。

## 输出给后续阶段的摘要

内部摘要至少包含：

```text
明确事实：...
业务规则：...
验收目标：...
页面/状态线索：...
缺失信息：...
冲突信息：...
可生成的测试风险：...
```

需求分析是测试意图的依据，不直接生成详细操作步骤或 XMind。
