# 测试用例生成规则

## 覆盖等级

- `minimal`：主流程或基本功能，加核心异常。
- `standard`：覆盖适用的主流程、中断、异常跳转、状态一致性、重复提交，或单页面的基本功能、边界、异常输入和字段依赖。
- `full`：覆盖所有可见分支、关键边界、状态恢复、联动和并发风险。

`focus_scenarios` 不为空时，只生成其中的场景；没有依据的场景必须在摘要中说明未生成原因。

过滤后若没有任何活动场景或用例，生成器会失败并提示 `focus_scenarios excludes all available scenarios`，避免产出空 XMind。

## 来源和假设

每条用例必须标记：

- `visible`：截图可见。
- `described`：用户明确描述。
- `inferred`：风险推导。

`inferred` 用例必须填写非空 `assumptions`，不能伪装成截图事实。

旧 Case Tree 如果省略来源，校验器会保守地补为 `source: inferred`、`confidence: low`，并在摘要中加入人工确认警告；显式来源和置信度不会被覆盖。

## 场景规则

跨页面：主流程、流程中断、异常跳转、状态一致性、重复提交并发防重。

单页面：基本功能、边界值、异常输入、字段依赖、稳定性。

每条用例只验证一个核心结果；步骤必须可执行，预期必须可观察；不得出现占位内容或无依据功能。

## 生成顺序

不要从原始截图或需求直接跳到详细步骤。先整理事实和页面/流程摘要，再设计测试意图，最后将意图展开为 Case Tree：

```text
事实 → 页面/流程摘要 → 测试意图 → 测试数据和步骤 → Case Tree
```

测试意图说明要验证的业务目标或风险；Case Tree 才记录前置条件、数据、步骤和预期。没有输入依据的场景可以不生成，但应在摘要中说明原因。

## 可观察预期

预期结果必须描述测试人员可以观察到的页面、提示、数据或状态变化。不要只写“系统正常”“功能正常”“校验通过”或“上传成功”；如果输入没有提供具体文案，不要编造文案，改为描述可观察的状态结果并降低置信度。

分类覆盖检查是 advisory warning，不是穷尽性证明。`full` 覆盖始终提示需要人工复核分支完整性。
